## Part A — FreeLLMAPI investigation (desktop installed v0.16.7, no gateway needed)

- Latest Windows release found via the GitHub API: **v0.16.7**, `FreeLLMAPI-Setup-0.16.7.exe`, 108.7 MB, published
  2026-10-21. Downloaded to `E:\hakawati-engines\FreeLLMAPI-Setup-0.16.7.exe` (SHA512 verified against the
  published `latest.yml` manifest), owner installed it and added provider keys himself.
- **Base URL**: `http://127.0.0.1:31415/v1` (desktop app; same port serves the dashboard and the API — confirmed
  from the Keys page header and a direct unauthenticated probe: `GET /v1/models` → `401 {"error":{"message":"Invalid
  API key","type":"authentication_error"}}`, matching the OpenAI wire format we already speak).
- **Unified key**: format `freellmapi-…`, shown masked in the dashboard. **Storage**: AES-256-GCM encrypted in
  `%APPDATA%\FreeLLMAPI\freeapi.db` (SQLite) with a separate `.encryption-key` file — confirmed via the project's
  own README ("Encrypted keys, one token out"). Did not attempt to read it: the harness itself blocked a plain
  `Get-Content` on `config.json` as credential materialization, which settled the design question outright — **no
  filesystem key-extraction, "the owner pastes it once" is correct and final**, not a fallback for a weaker plan.
- **`GET /v1/models`**: lists the whole catalog with `execution_status` (`ready` / `needsKey` / `exhausted`) per
  model; `?available=true` narrows to what can serve a request right now.
- **`X-Routed-Via: <platform>/<model>`**: confirmed from the public API reference — every answered response carries
  it; on a fallover, `X-Fallback-Attempts` / `X-Fallback-Trail` name each failed hop too.
- **`auto:smart` + an image**: confirmed — "When a request contains an image, the router restricts itself to
  vision-capable models and ignores text-only ones," independent of the `auto:*` suffix. No vision model enabled →
  `422 {"code":"no_vision_model"}`.

## Part B — code (branch `desktop/engines`, worktree `E:\hakawati-engines`)

- **`lib/settings.mjs`**: `freellmapi` preset added (`openai`, `http://127.0.0.1:31415/v1`, `auto:smart`).
  `engine.chain`: array of further engines tried after the fallback (same shape as `engine.fallback`, which is kept
  exactly as it was — the fallback slot is simply where FreeLLMAPI goes in the example chain `CodeCraft → FreeLLMAPI
  → optional LM Studio`). Masking/key-keep-on-save logic generalized to the whole chain.
- **`lib/llm.mjs`** (the bulk of the work): the old single `fallbackEngine()` path is now `restOfChain(engine)` =
  `[fallback, ...chain]`, tried in order. **Circuit breaker**: an engine that fails 2 calls in a row (its own
  retries exhausted) is skipped for 10 min — logged, and *never* skips the last engine left to try (a solo engine
  always gets its attempt). **Per-engine concurrency**: gates are now keyed by engine identity instead of one
  shared pair, so a chain member's `concurrency` is really its own. **Vision cache** generalized to every engine in
  the chain, not just the fallback. **`X-Routed-Via`** is captured from the response, logged (`via <engine> →
  <routed>`), and recorded in `.studio/llm-usage.jsonl`. `fetchModels()` and `testOneModel()` exported for the UI.
  `testEngine()` now tests the whole chain and returns both `fallback` (= chain[0], unchanged shape for old callers)
  and `chain` (every extra engine, in order).
- **`server.mjs`**: `GET /api/settings/models?which=primary|fallback|chain1|…` (the ⟳ Refresh button) and
  `POST /api/settings/test-model` (`{which, model}`, one pair at a time — "Test all models" paces itself from the
  client so free-tier per-minute limits aren't hit in one burst). `resetEngineHealth()` called after every settings
  save.
- **`public/app.js` / `app.css`**: the Fallback section gained a model datalist + ⟳ Refresh + Test all models
  (table: model / status / seconds / vision) — FreeLLMAPI naturally appears there since it's just a new preset in
  the same dropdown. A new "More engines" section lets the owner add/remove further chain entries (preset, model,
  protocol, base URL, key, with their own ⟳ Refresh — no per-row Test-all table, scope cut given the time budget:
  the headline Test-all feature lives on primary + fallback, which is where FreeLLMAPI actually sits in the
  documented example chain). Settings → Test now shows every chain member's result, not just one.

**Real pipeline run** (`node make.mjs new docs/test-story.en.txt --length 30` → `run <id> script,voice,cast,art`,
English sample story "The Star and the Lantern", FreeLLMAPI `auto:smart` primary, no CodeCraft fallover needed
since FreeLLMAPI answered every call):
- **Script**: 3 scenes, 5 shots, ~31 s, 2 script-doctor passes — all routed via `google/gemini-3.6-flash` /
  `gemini-flash-latest`.
- **Voice**: 5 lines, film runs 32.1 s — unaffected (edge-tts, not the text engine).
- **Cast**: 3 character portraits (Layla 18.5 s, Fox 11.9 s, Little Star 11.9 s).
- **Art**: all 5 shots produced (`PROGRESS 100% Drawing 7/7`, exit code 0, no hang). Picture quality held up, but
  **the single free-tier Gemini key became the bottleneck**: every Gemini alias FreeLLMAPI exposes shares that one
  account's rate limit, and this pipeline fires 3 candidates + a critic vision call concurrently (`concurrency: 2`).
  Result: `s2-1` passed cleanly (2 rounds, scored ≥7); `s1-1` and `s3-2` got reviewed but stayed under `minScore: 7`
  after `maxRounds: 2` (6/10, 5/10) and were kept as best-effort; `s1-2` and `s3-1` had the critic call itself
  exhaust all 6 retries on `429 rate_limit_exceeded` / `502` upstream errors and were **kept unreviewed** (the
  existing "unreviewed shots are re-judged without repainting on the next art run" behavior, not a crash). The
  reliability code (retry/backoff, per-engine gates) did its job — nothing hung or threw — but one free Gemini key
  is clearly under-provisioned for `candidates:3 + critic` at `concurrency:2`. **Recommendation for the owner**:
  add a second provider key in FreeLLMAPI (e.g. Groq or OpenRouter free tier) so the router has somewhere else to
  send the overflow, or lower `image.candidates`/`image.critic` concurrency when running on a single free key.
- CodeCraft fallback slot still confirms suspended (`403`) throughout — unrelated, expected, kept as-is for when
  it's reactivated.

**Follow-up (same day): a Groq key did *not* fix the critic bottleneck.** The owner added a free Groq key in
FreeLLMAPI and we re-ran `art` on the same project to re-judge the unreviewed/low-score shots. Final per-shot state
(from `project.json`):

| shot | reviewed | score | note |
|---|---|---|---|
| s1-1 | true | 6/10 | unchanged from the first run |
| s1-2 | **false** | — | still unreviewed — critic exhausted all 6 retries again |
| s2-1 | true | 5/10 | **regressed** from the first run's 7/10 pass — re-run repainted it from scratch (candidate scores aren't deterministic) |
| s3-1 | **false** | — | still unreviewed — critic exhausted all 6 retries again |
| s3-2 | true | 5/10 | unchanged |

Root cause confirmed from the live error text: `429` responses say "385 models skipped: no key configured for
their platform" and the retry trail only ever lists `google/*` routes — FreeLLMAPI's vision-capable routing pool
is still just the one Gemini key. Groq's models aren't selected for vision/critic calls (either not marked
vision-capable in the catalog, or not reachable on the free tier), so adding Groq only gives headroom to *plain
text* calls (confirmed earlier: 5 concurrent plain `test-model` calls all succeeded post-Groq), not to the picture
critic, which is the actual bottleneck in `art`.

**Real recommendation for the owner**: the fix has to be either (a) a second **vision-capable** free key behind
FreeLLMAPI (not just any free key), or (b) lower `image.candidates`/concurrency so the critic doesn't fire 3+
vision calls at once against one key, or (c) accept that some shots stay "unreviewed" on a single free vision key —
which is exactly what the existing unreviewed-shot fallback is for, and it degraded gracefully here (no hang, no
crash) rather than blocking the run.

**Follow-up: lowered `image.candidates` 3→2, re-ran `art` a third time.** Still 2 of 5 shots ended up unreviewed
(`s1-2`, `s3-2` this time — `s3-1` cleared at 5/10, so the unreviewed set just shifted, not shrank) and the log
still shows 11 separate `429`/`502` critic failures. **Candidate count was not the real lever** — `engine.concurrency`
(currently 2) lets two shots' critic calls race the same single Gemini key at once regardless of how many
candidates each shot paints; that's the more likely actual fix (serialize to `concurrency: 1` for the text engine),
still untried as of this report.

**Follow-up: `engine.concurrency` 2→1, re-ran `art` a fourth time — no change.** Exact same two shots (`s1-2`,
`s3-2`) stayed unreviewed, 12 more `429`/`502`s, and the error's `retryAtMs` jumped to "soonest reset ~5m" (up from
~40–80s in earlier runs). **Conclusion: this isn't a concurrency problem any more — it's that today's cumulative
testing (2 full test-all sweeps, 4 full `art` runs) has used up this one free Gemini key's quota for the day**, not
just its per-minute rate. Neither `candidates` nor `concurrency` can fix a quota that's already spent; the only
real levers left are a genuinely separate vision-capable key (different account/provider) or waiting for the quota
window to reset. Settings reverted: `image.candidates` back to 3, `engine.concurrency` back to 2 (today's two
changes didn't help, no reason to keep them lowered).
