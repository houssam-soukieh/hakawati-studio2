# T4 — Depth parallax strength tuning

**Status:** Done, no gateway used.

## Method
Reused the real rendering path (`buildBundle`/`openPlayer`/CDP screenshot pattern from `lib/render.mjs`,
reimplemented standalone to point at 3 patched player copies instead of touching the real `public/player.html`
or the teaser project's saved state). 3 of Kira's existing teaser keyframes, chosen for different camera moves:

| Shot | Camera | Size |
|---|---|---|
| `s1-2` | static | medium |
| `s1-6` | push-in | close |
| `s3-1` | pull-out | medium |

Depth maps generated fresh via `lib/video.mjs`'s `depthMap()` (Depth Anything V2 Large, direct call, not through
the project's `motion` step — kept it isolated from T3's held state) — 7–9s each, no issues.

3 variants of `player.html`'s L1 shader constants (line 127: `const OVERSCAN = 1.06, MARGIN = ..., AMP = 0.045,
ZOOM = 0.09, STEPS = 16`): **0.5×** (`AMP 0.0225, ZOOM 0.045`), **1.0×** (current), **1.5×** (`AMP 0.0675,
ZOOM 0.135`). Captured 3 frames per shot per variant (t = D×0.1, 0.5, 0.9) — 27 frames total, all clean (no
page errors, no WebGL context loss).

## Findings

**`s1-6` (close, push-in): current (1.0×) is the right default.** Progression across 0.5×→1.0×→1.5× is
clean and visible — 0.5× feels a little flat for a push-in on a close shot, 1.5× starts to feel aggressive
(noticeably tighter crop by the end, borders on over-animating a "close" rather than "extreme-close" shot).
1.0× reads as a natural, cinematic push.

**`s3-1` (medium, pull-out): no visible difference at all between 0.5×/1.0×/1.5×**, at either the start or
the end of the move. This isn't a measurement error — it's the shader's own margin cap doing its job:
`cap = min(1, MARGIN * 0.95 / (max(pivot, 1-pivot) * (AMP*wp + 0.5*ZOOM*wz)))` (player.html line 198) shrinks
proportionally as `AMP`/`ZOOM` grow, so once a shot's natural camera-move distance + pivot depth already
saturates the overscan margin at 1.0×, **multiplying the global constants by 1.5× just shrinks `cap` by the
same factor and cancels out** — the effective, post-cap displacement is identical. Confirmed by checking both
`t0` and `t2`: framing is pixel-close between the 0.5× and 1.5× variants throughout.

**`s1-2` (static): inconclusive from stills.** The "breathe" effect (`AMP * cap * 0.3 * sin(...)`) is a
continuous, small-amplitude oscillation — a single captured frame can land at any phase of it, so comparing
isolated stills across strengths isn't meaningful here. Would need a short clip/GIF across a few seconds to
judge properly; didn't do that given the time available. Flagging as a gap rather than guessing.

## Recommendation
**Don't blanket-raise the global `AMP`/`ZOOM` constants.** The effect is uneven: shots like `s1-6` would get
more aggressive (arguably past "natural" at 1.5×), while cap-bound shots like `s3-1` wouldn't change at all —
not a predictable uniform lever. If the goal is more visible depth on cap-bound shots specifically, the fix
belongs in the **cap formula itself** (e.g. raise `OVERSCAN`/loosen `MARGIN * 0.95`), not the nominal
`AMP`/`ZOOM` values — but that trades off edge-tearing margin, so I'd want the lead's call before touching it.
Current 1.0× defaults look right for the shots that aren't cap-saturated; no change recommended from this
sample.
